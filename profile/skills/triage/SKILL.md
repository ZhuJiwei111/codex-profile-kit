# Triage

Resolve the requested repository, issue/PR set, and read-versus-write scope.
Read the relevant reports, affected code, reproductions, and existing labels.
Use the configured tracker; do not run setup or assume a new workflow merely
because an optional tracker guide is absent.

Separate a reproducible defect, feature request, duplicate, unsupported report,
and material missing information. Validate the smallest concrete claim that can
change its classification. A report is not proof of a bug or permission to fix.

For a useful brief, retain the observed and expected behavior, evidence,
affected boundary, acceptance condition, and actual unresolved question. Ask
about a material user decision; do not turn every report into grilling or
domain-document updates. An explicitly named PR remains in scope regardless
of who authored it.

Default to a concise local assessment. Post comments, change labels, close
issues, or publish briefs only when explicitly authorized for those actions.
When posting, be transparent about automated assistance as the project requires.
Triage does not authorize code changes, merging, or contacting unrelated people.
