# Review context and continuity

## Resume and plan at the requested scale

Read user-linked tasks through the available task-reading tool. Page to the
relevant author decisions, filtering tool output rather than dumping whole
histories. Recover the document roles, accepted wording, pending package,
deferred items, review order, and synchronization/build authority. Historical
requests are context; do not execute experiments or other side work from them.

Verify the recovered state against the live ledger and target files. Preserve
completed edits and stable package IDs. When the author reopens an applied
passage, preserve the old application record and create a new linked package
anchored to the current source. Pending wording is replaced in its existing
package. Resume a deferred package in place after refreshing its anchor.

For an explicitly requested full review, read the current manuscript and
Supplement, reviewer letter, and current Response before giving a whole-paper
verdict. Inspect relevant figures and evidence; distinguish unread or unavailable
material. This grounding is done once, then refreshed only where changes matter.
For a single edit, read the local argument and its necessary dependencies.

When asked to plan the whole revision first, make a concise coverage inventory
in the ledger: stable ID, scientific question, target, dependency, and order.
Only the active item receives a full candidate. Honor choices such as Abstract
last or reviewer-specific replies before Editor/overall. Do not default to
expanding every candidate, creating another planning system, or repeatedly
renumbering the inventory.

If a claim moves to another section, name its destination and retain a coherent
argument during application. Include the dependent move in the same package
when deferring it would make the current passage incomplete. A future package
is not evidence that the contribution has already been preserved.

## Response review and manuscript revision

Record the document roles separately: submitted baseline, current manuscript,
current Response, revision ledger, and any author-requested clean bilingual or
TeX presentation. Each document has one canonical content owner; generated or
mirrored views follow that owner. A clean approved Response is a deliverable,
not another proposal ledger. Synchronize it only within the authorized scope.

For a fresh Response requested from scratch, start from the reviewer comment
and the author's argument. Include the complete reviewer comment in English
and faithful Chinese in package metadata. Read old replies as evidence leads;
do not import their structure or paste them into the ledger when the author
explicitly excludes them. Mark the original Response as absent for this new
draft. For optimization of an existing Response, display the actual current
Response and the full proposed replacement in both languages.

In a Response, give a brief acknowledgment, the direct supported answer, then
the evidence and necessary explanation. Use a result table for quantitative
comparisons and prose or a protocol table for evaluation-design questions.
Overall replies summarize conclusions and point to detailed replies without
duplicating them. Keep each concern focused; do not import another reviewer's
objections unless they materially affect this answer.

In a manuscript, organize motivation, findings, and interpretation as a scientific
argument. Put reproducibility details in Methods/Supplement and cite them from
the main text. Resource constraints may explain an evaluation choice in a
Response when requested; they need not become the paper's narrative. Introduce
new methods through the problem they solve. Include reviewer-suggested citations
where scientifically relevant without disrupting the existing story.

When Response review precedes manuscript revision, record each necessary
manuscript change as a dependency with its target and completion state. Approval
of a reply approves only its declared targets. Verify claims such as "we added"
or "the revised Methods now report" before treating them as completed actions;
keep wording describing planned manuscript changes explicitly provisional until
those changes are applied.

## Optional pipeline and bounded bookkeeping

Use subagents only when the author or applicable instructions authorize them;
follow `personal-subagent-boundaries` when available. For an approved exact edit,
give the worker exclusive target files, complete old/new anchors, approved
scope, and focused source checks. The worker edits those files only, returns
the result, and stops. The main agent owns judgment, questions, and ledger state.

While the worker applies the approved package, prepare evidence and wording for
the next independent package. Keep that preparation outside the active-package
state until the previous application is reconciled. Do not open a second active
package or write concurrently to worker-owned files. If the next proposal uses
those files, refresh its anchor after the worker completes before displaying it.

Use the worker's focused check results and inspect the actual affected change
once. Repeat checks only for new edits, failures, or unresolved uncertainty.
Do useful independent preparation before waiting; do not describe a dispatch
followed by immediate blocking and duplicate validation as acceleration.

The ledger owns package-level decisions and checks. Update any already-active
plan or project journal under its applicable rules at meaningful boundaries;
avoid copying every ordinary package into several status documents. Broader
authority or unresolved ownership conflicts still require a decision.
