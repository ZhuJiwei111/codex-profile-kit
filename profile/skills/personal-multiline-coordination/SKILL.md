# Personal Multiline Coordination

Root assigns complete tasks and shared resources. Task coordinators independently
complete their tasks. Optimize useful work and decision latency; documentation,
messages, checks, locks, and commits must not become another approval system.

## Authority And Roles

This skill grants no chat or execution authority. Use the user's current or
standing authorization; read referenced chats before relying on them. Carry
valid task-level authority forward without asking again at ordinary stages.
Respect scientific scope, explicit spending/resource boundaries, credentials,
external actions, and publication rights. A missing decision blocks only its
actual dependency path.

Root owns global priority, task assignment/lifecycle, resource allocation, and
cross-task conflicts. It does not automatically own task execution, document
editing, Git integration, or repeated acceptance. Assign integration or
maintenance work to a concrete task when needed. Each task coordinator owns its
plan, assigned resources, execution, repairs, continuation, checks, evidence,
documents, authorized commits, wakeups, and closure. Discussion owns scientific
analysis and experiment/analysis design, not operational scheduling.

Create persistent chats only with user authority for complete independent tasks.
Keep related phases, repairs, and container replacements in the same task.
Record a compact goal, acceptance, owner/write surface, resources/ETA, and state
entry point in existing project state; do not add a second coordination board.
An explicit succession preserves verified work and pending requirements.

## Dispatch Resources Without An Integration Gate

Under delegated compute authority, root checks task authority, ownership
conflicts, and only necessary live facts, updates the single allocation ledger,
and promptly sends the assignment. Reuse valid task/resource evidence; investigate
contradictions rather than redoing the task gate. Logs, replicas, labels, and
commits follow in later batches and never gate dispatch or authorized execution.

The task owner checks launch conditions, records adoption in task state, and
proceeds. Receipt, launch, first throughput, routine repair, internal milestone,
and ordinary commit do not require a chat report or root confirmation. Evidence
of acceptance is not a requirement to send an acknowledgment. A real transfer
of maintenance responsibility still needs an actual accepting owner, which can
be established from durable evidence without negotiation loops.

Allocate enough existing capacity for useful parallel work. ETA is a forecast,
not an invented minute cap or retry quota. Continuing allocation spans related
repairs/checks; do not return and re-request it at each stage. Return capacity
when substantially idle or only CPU wrap-up remains. Preserve needed protection
until its receiving owner takes responsibility. Returning GPUs does not itself
authorize deleting data, terminating containers, or buying external resources.

## Communicate Only For A Recipient Action

Message for assignment/scope changes, shared-resource requests/returns,
cross-task decisions or risks, ETA changes affecting other commitments, and
complete delivery. Include the necessary change/action and evidence pointer;
batch related matters. Otherwise save state and keep working. "No reply needed"
does not justify a redundant message. Do not wake a chat merely to observe it;
use compact status/wait tools at actual coordination points.

Handle urgent risks, authority corrections preventing a current wrong action,
and genuine cross-task blockers immediately on the affected path. Register
ordinary requirements with source, unfinished action, and continuation point
in the existing TODO/card; process in batches. Close the current batch without
absorbing every nonurgent arrival. Preserve pending work and latest effective
authority when accepting it, refresh before handoff/foreseeable compaction,
and reread after resumption. A summary must not revive superseded constraints.

When authorized, send discussion chats scientific questions, necessary results,
protocol limitations, and evidence. Discussion can submit a formed experiment
request to root; keep operational queues, resource ETAs, and progress chasing
out of scientific discussion. A design proposal is not new compute authority.

## Direct State Editing And Proportionate Checks

Authorized coordinators directly maintain their own TODO/card entries and
sourced journal events. Do not ask root to write or submit each routine update.
Keep one canonical fact and point to it; do not demand multiple synchronized
summaries or fixed evidence forms for every stage. Task owners perform the
checks needed by the actual acceptance; root does not repeat sufficient work.

Exclusive files need no generic lock. For actual concurrent shared-file writes,
use the existing short mutual exclusion around reread, precise patch, atomic
save, and readback; never hold it across computation or remote waits. Atomic
rename alone does not prevent lost updates. On contention, keep the pending
change and do independent work, without chat negotiations or stealing locks.
Separate SSH endpoints may share one filesystem; preserve others' increments.

When commits are authorized, task coordinators commit checked owned changes.
Shared-index stage/commit operations must serialize briefly using the project's
mechanism, without making root the permanent Git operator. Existing staged work
or a busy index defers that Git operation, not execution; preserve stable paths
for a later batch or a concrete integration task. Do not overwrite others'
changes. Commit authority does not imply push authority.

Use bounded subagents or existing container agent CLIs when independent local
analysis, implementation, or review outweighs startup/context/review costs.
Follow personal-subagent-boundaries, give minimal useful context and exclusive
writes, and accept concrete outputs without repeating the whole task. Keep CLI
monitor sessions separate and use current interfaces/permissions. Mechanical
probes and simple resource decisions remain direct operations.

## Wakeups And Closure

The task owner maintains its actual follow-up mechanism. Keep App heartbeats
paused during active work; arm only a useful future action while waiting that
existing completion events do not cover. Reschedule on meaningful ETA changes,
pause when no autonomous action exists, and disable on completion/cancellation.
Keep unchanged states quiet. Container monitoring, resource protection, and
authorized deterministic continuation stay independently owned and active.
Root watches only global resource/expiry/cross-task decisions, not each stage.

The task owner verifies the original acceptance, saves results and remaining
owners, hands off resources, stops obsolete wakeups, and delivers once. Root
handles the next task/resource decision and authorized archival, not another
stage-by-stage review. Archive completed chats when evidence and residuals are
preserved and the chat has ended; respect retention requests. Archival does not
stop processes or delete evidence. Report only observed execution and Git/chat
state. Read references/source-notes.md only for provenance maintenance.
